线上故障排查：3个真实案例的复盘与总结

2026-09-22 · 实战

理论千遍不如实战一遍。这篇文章记录了完整的项目复盘，包含踩过的坑和最终的解决方案。

核心要点

本文将从以下 3 个方面展开，带你系统掌握相关知识：

  1. 网关层做统一认证和限流
  2. 服务间通信：同步用gRPC，异步用消息队列
  3. 服务拆分原则：按业务边界而非技术层

1. 网关层做统一认证和限流

把认证、限流、日志、跨域这些横切关注点放在网关层统一处理，后端服务只关注业务逻辑，避免重复造轮子。

# 网关层职责
- JWT Token 校验
- API 调用频率限制
- 请求/响应日志
- 跨域处理
- 服务路由与负载均衡

# 后端服务职责
- 业务逻辑
- 数据持久化
- 领域事件

2. 服务间通信：同步用gRPC，异步用消息队列

需要立即响应的用gRPC（高性能、强类型），不需要立即响应的用消息队列（解耦、削峰）。不要用HTTP REST做内部服务调用。

# 同步调用：订单创建后立即查用户信息
# order-service -> gRPC -> user-service

# 异步通知：订单支付成功后发事件
# payment-service -> Kafka -> order-service
# payment-service -> Kafka -> inventory-service
# payment-service -> Kafka -> notification-service

3. 服务拆分原则：按业务边界而非技术层

微服务拆分最常见的错误是按技术层拆（API服务、逻辑服务、数据服务）。正确的做法是按业务领域划分，每个服务有完整的业务闭环。

# 错误：按技术层拆分
services/
  api-gateway/
  business-logic/
  data-access/

# 正确：按业务领域拆分
services/
  order-service/      # 订单完整生命周期
  payment-service/    # 支付全流程
  inventory-service/  # 库存管理
  user-service/       # 用户与权限

对比参考表

为了方便你快速对比和记忆，这里整理了一个汇总表格：

组件 选型 理由
服务网关 Kong / APISIX 性能好、插件丰富、社区活跃
服务通信 gRPC 强类型、高性能、跨语言
消息队列 Kafka 高吞吐、持久化、生态成熟
服务发现 Consul / K8s DNS 健康检查 + DNS 集成

最佳实践

  • 先测量再优化，用数据说话，不要凭感觉
  • 建立性能基准，每次优化后对比结果
  • 考虑边际收益，花1天提升10%不如花1天提升2倍

总结

性能优化是一个持续的过程，不是一劳永逸的。建立性能基准、定期复测、根据数据决策，比记住多少技巧都重要。希望这篇文章能帮你建立正确的优化思路。
